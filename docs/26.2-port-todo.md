## 2. 重要教训：编译通过 != mixin 能在运行时应用

挂起渲染文件后，构建一度是绿的，但 `runClient` **仍然崩溃**：

    Mixin apply for mod itemglintrelight failed
      itemglintrelight.client.mixins.json:GlTextureViewAccessor
      -> com.mojang.blaze3d.opengl.GlTextureView
    InvalidAccessorException: No candidates were found matching
      getFbo(Lcom/mojang/blaze3d/opengl/DirectStateAccess;Lcom/mojang/blaze3d/textures/GpuTexture;)I

原因：`@Invoker("getFbo")` / `@Accessor("...")` 的目标是用**字符串**写的，
编译器无法校验；目标方法在 26.2 消失也不会报编译错，只在运行时炸。

**因此：每次改动 mixin 配置后，必须实际跑一次 `runClient` 看日志，不能只看 build 是否绿。**
本次就是靠实测发现并修掉这个崩溃的。

## 2.5 物品组件延迟绑定（UI 崩溃根因，已修）

26.2 的物品 data components 是**延迟绑定**的：在标题界面（尚未进入世界）时
`Holder$Reference#components()` 会抛 `NullPointerException: Components not bound yet`，
因此**此时构造任何 `ItemStack` 都会崩溃**。

实测证据（首个客户端 tick，标题界面，资源已重载完）：

    [DIAG] diamond holder componentsBound=false levelLoaded=false
    new ItemStack(DIAMOND_SWORD) FAILED
      NullPointerException: Components not bound yet
        at Holder$Reference.components(Holder.java:281)
        at ItemStack.<init>(ItemStack.java:265)

这导致 ModMenu 在标题界面打开配置界面时报错：

    (Mod Menu | ModsScreen) Error from mod 'itemglintrelight'
    NullPointerException: Components not bound yet
      at ItemGlintRelightConfigScreen.<init>(ItemGlintRelightConfigScreen.java:130)
      at com.terraformersmc.modmenu.ModMenu.getConfigScreen

**修复**：任何 `ItemStack` 构造前先判断组件是否已绑定，未绑定则退化为 `ItemStack.EMPTY`：

    private static boolean itemsBound() {
        return Items.DIAMOND_SWORD.builtInRegistryHolder().areComponentsBound();
    }
    private ItemStack previewItem = itemsBound() ? new ItemStack(Items.DIAMOND_SWORD) : ItemStack.EMPTY;

并给 `rebuildItemChoices()` / `rebuildRuleTargetChoices()` 的注册表遍历加了同样守卫
（这两处原本对每个物品都构造 `ItemStack`）。

**验证**：强制在标题界面打开配置屏并渲染约 40 秒 —— 构造成功、无异常、无崩溃报告。
**影响**：配置界面在标题界面可正常打开；此时物品选择器列表为空（组件未绑定），
进入世界后打开则正常填充。

## 3. 26.2 渲染层是重构而非改名

26.2 移除了本项目自绘管线依赖的核心类型（经官方 NeoForge 26.1 -> 26.2 Primer 与 jar 反射确认）：

- `MultiBufferSource` **接口被移除**，由 feature / SubmitNode 系统取代
- `OutlineBufferSource` **被移除**
- `RenderBuffers#bufferSource / outlineBufferSource` -> `stagedVertexBuffer`
- `RenderPipeline.Builder`：`withSampler / withUniform` -> `withBindGroupLayout`
- `withVertexFormat(format, mode)` -> `withVertexBinding(index, format)` + `withPrimitiveTopology(...)`
- `withDepthWrite / withDepthTestFunction` -> `withDepthStencilState(DepthStencilState)`；`DepthTestFunction` 已不存在
- `TextureTarget` / `RenderTarget` 现在需要 `GpuFormat`
- `GlDevice` 不再是 public（`DirectStateAccess` 的方法反而变为 public）

> **这与 Vulkan 无关**：即使只用 OpenGL，上述类型也已被替换。
> 官方 primer 全文见 `research/primer-26.2.md`（另有 26.1 / 26.3 / 1.21.11 版本对照）。

## 8. 第一人称描边 v1（纯色，无 bloom）

### 做法：复用原版描边通道，不写自定义管线

26.2 的提交签名保留了 outline 颜色参数：

    ItemStackRenderState#submit(PoseStack, SubmitNodeCollector, int light, int overlay, int outlineColor)

第 5 个 int 是 **outlineColor**；非零时 `ItemFeatureRenderer.prepareOutlineSubmit` 会走
`RenderType.outline()` 提交一条描边。因此第一版**不需要** mask / 合成 / 自定义 RenderPipeline。

新增三处（均在 26.2 侧）：

| 文件 | 作用 |
|---|---|
| `client/render/FirstPersonOutlineState.java` | 维护第一人称手部渲染窗口；按配置解析描边色 |
| `mixin/client/ItemInHandRendererOutlineMixin.java` | 在 `submitArmWithItem` 前后开/关窗口 |
| `mixin/client/ItemStackRenderStateOutlineMixin.java` | `@ModifyVariable(index = 5)` 覆写 outlineColor |

颜色取 `ItemGlintRelightConfig#outlinePrimaryColor()`，并遵循
`outlineEnabled()` / `outlineMainHand()` / `outlineOffHand()`，
per-item 规则经 `DisplayRuleManager.resolve`。

### 26.2 方法改名（重要）

`ItemInHandRenderer` 的方法**改了名**，照抄 1.21.11 的名字会在运行时注入失败：

| 1.21.11 | 26.2 |
|---|---|
| `renderHandsWithItems` | `submitHandsWithItems` |
| `renderArmWithItem` | `submitArmWithItem` |
| `renderPlayerArm` / `renderMapHand` / `renderItem` | 未变 |

`renderArmWithItem` -> `submitArmWithItem` 的改名就是本轮踩到的坑：编译通过，
但运行时 `InvalidInjectionException: Critical injection failure` 并直接崩溃。

- **但描边的实际视觉效果未经验证**：第一人称描边需要「世界内手持物品」，

## 13. 第一人称描边修复完成：26.2 的 reverse-Z

**结果：用户实机确认「描边正常了」。** 症状原为「描边是空心的，柔和度越小描边越细并且越卡顿」。

### 13.1 根因：深度约定从 normal-Z 翻转成 reverse-Z

26.2 把深度约定整体翻转了，三条独立证据：

1. `glClipControl`：`GlDevice` 初始化时调用 `ARBClipControl.glClipControl(36001, 37727)`
   = `(GL_LOWER_LEFT, GL_ZERO_TO_ONE)`。
2. `RenderPipelines` 里 `CompareOp.GREATER_THAN_OR_EQUAL` 出现 **14** 次，
   `LESS_THAN_OR_EQUAL` **0** 次。
3. vanilla 清深度一律用 `dconst_0` = **0.0**（`LevelRenderer` 的
   `clearDepthTexture(tex, 0.0)` / `clearColorAndDepthTextures(..., depthTex, 0.0)`）。

即：**近平面 = 1.0，远平面 = 0.0**（1.21.11 是近 0.0 / 远 1.0）。

实测验证：在渲染器里临时回读 mod 捕获的投影矩阵，得到
`m22 = 5.0025014E-4, m32 = 0.050025012, m23 = -1.0`。
按 26.2 约定解出 **near = 0.05、far = 100**（按 normal-Z 解会得到 near=100 > far=0.05，荒谬）。
→ reverse-Z 成立。

### 13.2 为什么表现为「空心 / 变细 / 卡顿」

共享着色器（`common/src/main/resources/.../shaders/core/`）里的深度比较全是 normal-Z 写法：

    visible = smoothstep(nearestDepth - 0.0004, nearestDepth + 0.0003, sceneDepth);
    if (sceneDepth + 0.00015 < nearestDepth) discard;

在 reverse-Z 数据下这套判断被整体取反，于是：

- 描边像素的可见性不再由「物品是否被遮挡」决定，而是由**背景深度与物品深度的巧合接近程度**决定
  → 只在背景恰好贴近物品的轮廓段上留下像素 → **断续、像空心的轮廓**；
- `sceneDepth` 稍微变化就从 1 掉到 0 → 取样方向稍有不同结果就跳变 → 看起来**细且抖**。

### 13.3 修法：在采样边界把深度镜像回来（单个开关，不动 1.21.11）

反向投影存储的深度**恰好**是 `1 - z`，所以在着色器里读到深度后立刻镜像回来，
下游所有 1.21.11 的数学就原样成立，不需要改任何比较式：

    float normalDepth(float depth) {
        return bloomParameters.z > 0.5 ? 1.0 - depth : depth;
    }

- 开关放在已有 uniform `OutlineInfo.bloomParameters.z`（原本恒为 0）。
- **26.2 的 Java 侧写 1.0**（`REVERSE_Z_FLAG`），**1.21.11 的 Java 侧不写**（仍是 0.0）
  → 同一份共享着色器，两边各按自己的约定工作，1.21.11 行为零变化。
- 涉及文件：`held_item_outline.fsh`、`held_item_bloom_composite.fsh`、
  `held_item_gui_composite.fsh`、`third_person_bloom_composite.fsh`（各 1～6 处采样点）。

**Java 侧同步修正**（原来全是 1.21.11 的 far=1.0）：
所有深度清除 `1.0D` -> `0.0D`，共 5 处：
`clearDepthTexture(mainTarget...)`、`clearDepthTexture(thirdPersonSceneDepth...)`、
`clear(TextureTarget)`、`clearMask(...)` 两处（含带 region 的重载）。
这一并修正了 1x1 arm-occluder 占位目标：它清成 0.0 后经 `normalDepth` 映射回 1.0，
`armDepthPresence(1.0) == 0`，即「没有手臂」——语义与 1.21.11 一致。

### 13.4 顺带修好：投影矩阵从未被捕获

排查中发现 `levelProjectionMatrix` / `handProjectionMatrix` **恒为 null**，

## 14. bloom「只有卡顿、没有效果」的结论：它就是 §13 那一处 reverse-Z

**用户实机确认：bloom 效果完全正常。bloom 代码本身不需要改。**

### 14.1 为什么之前看不到

`held_item_bloom_composite.fsh` 的主流程：

    float blurredCoverage = max(texture(BloomSampler, texCoord).a - texture(MaskSampler, texCoord).a, 0.0);
    ...
    bool hasVisibleItem = false;
    for (3x3) {
        float sampleItemDepth = texture(ItemDepthSampler, sampleUv).r;
        if (thirdPerson || texture(SceneDepthSampler, sampleUv).r + 0.00015 >= sampleItemDepth) {
            itemDepth = min(itemDepth, sampleItemDepth); hasVisibleItem = true;
        }
    }
    if (!hasVisibleItem) discard;

在 reverse-Z 数据下这个比较被取反：背景深度**永远小于**物品深度，9 个采样点全部不满足，
`hasVisibleItem` 恒为 false -> **整趟 pass 每个像素都 discard**。
而 2 次清屏 + 4 趟模糊 + 1 趟合成（每只手一套，共 7 趟 x2）照样发出 -> **只有卡顿、没有效果**，
和用户描述完全一致。§13 的 `normalDepth()` 让这个比较重新成立，bloom 随即正常。

### 14.3 顺带得到的两个实测结论（供后续参考）

1. **合成 scissor 仍为 null**。即使补上了 §13.4 的投影捕获，运行时 `resolveCompositeScissor` 依然返回 null。
   `isPerspectiveProjection`（`|m33| < 0.5`）对该投影成立，所以更可能是
   `state.itemBounds == null` 且 `itemPoseMatrix/modelViewMatrix` 缺失，或 `handPassMatrix` 在
   `snapshotRenderContext` 时尚未置位。纯性能项，不影响画面。
2. **两条回读路子在 26.2 都不可用**，后续做 GPU 侧诊断不要再走这两条：
   - `GlTextureView/`FBO 路子：`RenderSystem.getDevice()` 返回的是
     `com.mojang.blaze3d.systems.GpuDevice`（不是 `opengl.GlDevice`），`framebufferId()` 恒为 0；
   - `CommandEncoder#copyTextureToBuffer`：回调是**异步**的（实测 `callbackDone` 恒 false），
     同一帧内 `map` 读到的是空 buffer；
   - `glBindTexture` + `glGetTexImage`：在 26.2 的 DSA 上下文里对 color 纹理读回全 0。
   结论：GPU 侧诊断要么走 `PictureInPictureRenderer` 之类的正规通道，要么靠肉眼/日志推断。

## 15. P3 完成：配置界面物品预览的描边

**状态：`ItemPreviewRenderer` 已补上描边，实测跑通（见 15.3）。**

### 15.1 之前为什么没有

26.2 的 `ItemPreviewRenderer` 是「缩减版移植」，文件头注释就写明
「the outline compositing pass is intentionally not implemented yet -- only the item itself is rendered」。
而 `HeldItemOutlineRenderer` 侧的预览合成 API（`compositePreviewToTexture` / `renderGuiBloom` /
`writePreviewUniforms` / 预览 bloom 目标 / preview 管线）**早就移植好了**，只是没人调用。

### 15.2 移植内容

`ItemPreviewRenderer.renderToTexture` 现在按 1.21.11 的两遍结构重写：

1. 用 mod 自己的 `SubmitNodeStorage` + `FeatureRenderDispatcher` + `RenderBuffers(1)` 把物品
   **画进 PIP 颜色目标**，然后 `buffers.endFrame()` 刷出；
2. 建/复用私有 `outlineMask`（`TextureTarget(..., true, RGBA8_UNORM)`），清成
   `HeldItemOutlineRenderer.clearColor()` + `farDepth()`，把
   `RenderSystem.outputColorTextureOverride/outputDepthTextureOverride` 指向它，再提交一次物品并渲染，
   finally 里还原两个 override；
3. `HeldItemOutlineRenderer.compositePreviewToTexture(minecraft, config, outlineMask, colorTarget,
   depthTarget, resolvePreviewMaterialPalette(itemState, config), state.outlineScale())`。

**26.2 的关键差异（必须注意）：**

| 点 | 1.21.11 | 26.2 |
|---|---|---|
| `renderToTexture` 签名 | `(state, PoseStack)`，物品提交进 mod 自己的 storage | `(state, PoseStack, SubmitNodeCollector)` |
| 谁画物品 | mod 自己（super 不碰 storage） | **collector 是 PIP 自带的 storage，但 `prepare` 是在 `renderToTexture` 返回之后才 `renderAllFeatures` 回放它** —— 若把物品丢给 collector，物品会画在描边**之上** |
| 结论 | — | **必须自己提交+渲染物品，让 collector 保持为空**（`renderAllFeatures(空 storage)` 是 no-op） |
| `FeatureRenderDispatcher` | `(storage, BlockRenderer, BufferSource, AtlasManager, OutlineBufferSource, CrumblingBufferSource, Font)` + 无参 `renderAllFeatures()` | `(RenderBuffers, ModelManager, AtlasManager, Font, GameRenderState)` + `renderAllFeatures(SubmitNodeStorage)` |
| 刷帧 | `bufferSource/outlineBufferSource/crumblingBufferSource` 三个 endBatch | `RenderBuffers#endFrame()` |
| 清 mask 的深度 | `1.0D` | `HeldItemOutlineRenderer.farDepth()`（reverse-Z 远平面 = **0.0**） |

PIP 的 `prepare` 会先把 `outputColorTextureOverride/outputDepthTextureOverride` 指向 PIP 的纹理**再**调
`renderToTexture`（已用 `javap` 确认字节码顺序），所以 `renderToTexture` 里读到的两个 override 就是
PIP 的颜色/深度目标，与 1.21.11 一致。

顺带在 `HeldItemOutlineRenderer` 暴露了两个把 reverse-Z 知识集中的公共方法：
`clearColor()` 与 `farDepth()`，避免预览侧再硬编码 `0.0`。

### 15.3 验证方法（可复用）

配置界面只能按键打开，无法用脚本交互。临时在 `ItemGlintRelightClient` 里加了一个
「存在 `run/auto-preview.txt` 就 60 tick 后自动打开配置界面」的钩子，跑一次实机：

    [PreviewOutline] mask orders=1 target=146x280     <- 快速预览面板
    [PreviewOutline] mask orders=1 target=456x252     <- 主预览面板

- `orders=1` 证明物品确实被提交进 mask 并渲染出来了（mask 非空，描边才有源）；
- 两个不同尺寸说明主面板与快速预览面板两条路径都命中了新的代码；
- 全程无异常、无 mixin 失败。
- **验证完成后该钩子与触发文件都已删除**（`git status` 里已无 `ItemGlintRelightClient.java`）。

### 15.4 顺带修掉一个上一轮引入的隐患

26.2 的 HUD 与**每个 GUI picture-in-picture 渲染器**都会走
`ProjectionMatrixBuffer#getBuffer(Projection)`——也就是 §13.4 新增的那个捕获点。
原先没有作用域限制，GUI 阶段上传的投影会**覆盖掉手部投影矩阵**，
下一帧 `snapshotRenderContext` 拿到的就是 GUI 投影，一旦合成 scissor 重新生效就会算错。

修法：新增 `worldProjectionCaptureOpen`，`beginFrame()` 置真、`endHandPass()` 置假
（GUI 一定在 `endHandPass` 之后），并用 `isWorldProjectionCaptureOpen()` 守住两个注入点。

## 16. 光影（Iris）兼容现状与已修缺陷

### 16.1 现状：Iris 代码已全量移植，但只覆盖第三人称

`HeldItemOutlineRenderer` 里 Iris 相关代码 **1.21.11 与 26.2 各 70 处、逐条一致**（只是行号平移），
说明移植时全量带过来了。但逐条核对后确认：**这些全部服务于第三人称**
（`getIrisNoHandDepthTexture` / `copyIrisNoHandDepth` / `isIrisShaderPackRendering` /
`iris_render_tail` / `irisCaptureProbe` / `[ThirdPersonIrisProbe]`）。
**第一人称没有任何 Iris 分支**——1.21.11 里也没有，所以这一块不存在「照抄的源」。

`HeldItemOutlineCompat` 的反射目标已逐项对照 `D:\workplace\Iris-26.2` 源码核验，**全部仍然成立**：

| mod 侧调用 | Iris-26.2 现状 |
|---|---|
| `IrisApi#getInstance/isShaderPackInUse/isRenderingShadowPass` | `common/src/api/.../v0/IrisApi.java` 均在 |
| `Iris#isPackInUseQuick` | `common/.../iris/Iris.java:764` |
| `Iris#getPipelineManager` | `Iris.java:672` |
| `PipelineManager#getPipelineNullable` | `pipeline/PipelineManager.java:51` |
| pipeline 内类型为 `net.irisshaders.iris.targets.RenderTargets` 的字段 | `pipeline/IrisRenderingPipeline.java:123` `private final RenderTargets renderTargets;` |
| `RenderTargets#getDepthTextureNoHand` | `targets/RenderTargets.java:151`，返回 `GpuTexture` |

即 `HeldItemOutlineCompat` **不需要改**。

### 16.2 已修：`framebufferId()` 恒返回 0，导致 Iris depthtex2 路线必然失败

- 26.2 的 `RenderSystem.getDevice()` 返回 **`com.mojang.blaze3d.systems.GpuDevice`**（包装层），
  不是 `com.mojang.blaze3d.opengl.GlDevice`；原来的 `instanceof GlDeviceAccessor` 永远为假，
  `framebufferId()` 恒为 0。
- 后果不只是「少了个优化」：`copyIrisNoHandDepth` 里 `destinationFbo <= 0` → 直接
  `irisNoHandDepthStatus = "destination_fbo_unavailable"` 返回 false，
  **Iris 的 depthtex2 场景深度路线在 26.2 上根本走不通**（第三人称会退到
  `iris_depth_unavailable` 诊断分支）。
- 修法：`GpuDevice` 有 `private final GpuDeviceBackend backend`，而
  `class GlDevice implements GpuDeviceBackend`。新增 `mixin/client/GpuDeviceAccessor.java`
  取该字段（返回类型必须是公开接口 `GpuDeviceBackend`，写成 `Object` 会被 Mixin 报
  `InvalidAccessorException`），再 `instanceof GlDeviceAccessor` 拿到 `DirectStateAccess`。
- **实测确认**：`[FboProbe] framebuffer lookup works now fbo=4`，无 mixin 失败、无崩溃。

### 16.3 第一人称的 Iris 缺口（尚未实现）

第一人称合成分两步：`ItemInHandRendererMixin` 抓取手部节点，`GameRendererFrameMixin` 在
`renderItemInHand` RETURN 调 `composite(...)` → `renderCapture` 把物品重放进 mask →
`submitComposite` 合成到主目标。其中场景深度**无条件**用
`mainTarget.getDepthTextureView()`。

问题在于（§15 那段注释已写明）：**Iris 用自己带 z-压缩投影的手部程序写层级深度，且在该深度上
还跑了多个全屏 pass**，所以

- `SceneDepthSampler`（主目标深度，Iris 空间）与
- `ItemDepthSampler`（mod 用游戏投影重放进 mask 的深度）

**不在同一深度空间**，比较结果无意义，描边会被错误裁掉/残缺。既有代码对第一人称的应对只是
「把手部arm重放进自己的 mask，让手臂遮挡不依赖场景深度」，遮挡项解决了，但 `SceneDepthSampler` 没有。

**已实现的移植方案**（与第三人称既有路线同构）：

1. `submitComposite` 的 6 参重载（第一人称与合并手部路径）在
   `HeldItemOutlineCompat.isIrisShaderPackRendering()` 为真时，用现成的 `copyIrisNoHandDepth(...)`
   把 Iris 的 `depthtex2`（`noHand`，手之前的场景深度）拷进新增的私有目标
   `irisHandSceneDepth`，并把它作为 `sceneDepthView`；
2. 拷贝不可用（或 `-Ditemglintrelight.irisHandSceneOcclusion=false`）时退到**关闭场景遮挡**模式，
   而不是拿两个不同深度空间的数值硬比；
3. 遮挡模式统一走 `OutlineInfo.scrollBounds.z`（`OCCLUSION_SCENE=0` / `OFF=1` /
   `THIRD_PERSON=2`）；`writeUniforms` 的 `boolean thirdPerson` 改为 `int occlusionMode`。
   `held_item_outline.fsh` 早有 `sceneOcclusionEnabled()`；`held_item_bloom_composite.fsh`
   补上同名判定与 `!sceneOcclusionEnabled()` 旁路，两个着色器的语义就此对齐。
4. `irisHandSceneDepth` 只做深度拷贝、不参与物品 mask，与第三人称的 `thirdPersonSceneDepth`
   互不干扰。

**顺带修正一处设计问题**：`armOcclusion` 原先放在 `sceneOcclusionEnabled()` 块内。但手臂遮挡用的是
mod 自己重放的 `ArmOccluderSampler`/`ArmOccluderDepthSampler`，与场景深度无关——这正是当初把手臂
重放进独立 mask 的目的（见第一人称 arm 注释）。现已移到块外：模式 0/2 行为等价
（`visible` 已为 0 或已 discard 时结果不变），而模式 1 仍保留手臂遮挡。
