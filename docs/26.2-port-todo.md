## 2. 重要教训：编译通过 != mixin 能在运行时应用

挂起渲染文件后，构建一度是绿的，但 `runClient` **仍然崩溃**：

    Mixin apply for mod itemglintrelight failed
      itemglintrelight.client.mixins.json:GlTextureViewAccessor
      -> com.mojang.blaze3d.opengl.GlTextureView
    InvalidAccessorException: No candidates were found matching
      getFbo(Lcom/mojang/blaze3d/opengl/DirectStateAccess;Lcom/mojang/blaze3d/textures/GpuTexture;)I

原因：`@Invoker("getFbo")` / `@Accessor("...")` 的目标是用**字符串**写的，
编译器无法校验；目标方法在 26.2 消失也不会报编译错，只在运行时炸。

**因此：每次改动 mixin 配置后，必须实际跑一次 `runClient` 看日志，不能只看 build 是否绿。**
本次就是靠实测发现并修掉这个崩溃的。

## 2.5 物品组件延迟绑定（UI 崩溃根因，已修）

26.2 的物品 data components 是**延迟绑定**的：在标题界面（尚未进入世界）时
`Holder$Reference#components()` 会抛 `NullPointerException: Components not bound yet`，
因此**此时构造任何 `ItemStack` 都会崩溃**。

实测证据（首个客户端 tick，标题界面，资源已重载完）：

    [DIAG] diamond holder componentsBound=false levelLoaded=false
    new ItemStack(DIAMOND_SWORD) FAILED
      NullPointerException: Components not bound yet
        at Holder$Reference.components(Holder.java:281)
        at ItemStack.<init>(ItemStack.java:265)

这导致 ModMenu 在标题界面打开配置界面时报错：

    (Mod Menu | ModsScreen) Error from mod 'itemglintrelight'
    NullPointerException: Components not bound yet
      at ItemGlintRelightConfigScreen.<init>(ItemGlintRelightConfigScreen.java:130)
      at com.terraformersmc.modmenu.ModMenu.getConfigScreen

**修复**：任何 `ItemStack` 构造前先判断组件是否已绑定，未绑定则退化为 `ItemStack.EMPTY`：

    private static boolean itemsBound() {
        return Items.DIAMOND_SWORD.builtInRegistryHolder().areComponentsBound();
    }
    private ItemStack previewItem = itemsBound() ? new ItemStack(Items.DIAMOND_SWORD) : ItemStack.EMPTY;

并给 `rebuildItemChoices()` / `rebuildRuleTargetChoices()` 的注册表遍历加了同样守卫
（这两处原本对每个物品都构造 `ItemStack`）。

**验证**：强制在标题界面打开配置屏并渲染约 40 秒 —— 构造成功、无异常、无崩溃报告。
**影响**：配置界面在标题界面可正常打开；此时物品选择器列表为空（组件未绑定），
进入世界后打开则正常填充。

## 3. 26.2 渲染层是重构而非改名

26.2 移除了本项目自绘管线依赖的核心类型（经官方 NeoForge 26.1 -> 26.2 Primer 与 jar 反射确认）：

- `MultiBufferSource` **接口被移除**，由 feature / SubmitNode 系统取代
- `OutlineBufferSource` **被移除**
- `RenderBuffers#bufferSource / outlineBufferSource` -> `stagedVertexBuffer`
- `RenderPipeline.Builder`：`withSampler / withUniform` -> `withBindGroupLayout`
- `withVertexFormat(format, mode)` -> `withVertexBinding(index, format)` + `withPrimitiveTopology(...)`
- `withDepthWrite / withDepthTestFunction` -> `withDepthStencilState(DepthStencilState)`；`DepthTestFunction` 已不存在
- `TextureTarget` / `RenderTarget` 现在需要 `GpuFormat`
- `GlDevice` 不再是 public（`DirectStateAccess` 的方法反而变为 public）

> **这与 Vulkan 无关**：即使只用 OpenGL，上述类型也已被替换。
> 官方 primer 全文见 `research/primer-26.2.md`（另有 26.1 / 26.3 / 1.21.11 版本对照）。

## 8. 第一人称描边 v1（纯色，无 bloom）

### 做法：复用原版描边通道，不写自定义管线

26.2 的提交签名保留了 outline 颜色参数：

    ItemStackRenderState#submit(PoseStack, SubmitNodeCollector, int light, int overlay, int outlineColor)

第 5 个 int 是 **outlineColor**；非零时 `ItemFeatureRenderer.prepareOutlineSubmit` 会走
`RenderType.outline()` 提交一条描边。因此第一版**不需要** mask / 合成 / 自定义 RenderPipeline。

新增三处（均在 26.2 侧）：

| 文件 | 作用 |
|---|---|
| `client/render/FirstPersonOutlineState.java` | 维护第一人称手部渲染窗口；按配置解析描边色 |
| `mixin/client/ItemInHandRendererOutlineMixin.java` | 在 `submitArmWithItem` 前后开/关窗口 |
| `mixin/client/ItemStackRenderStateOutlineMixin.java` | `@ModifyVariable(index = 5)` 覆写 outlineColor |

颜色取 `ItemGlintRelightConfig#outlinePrimaryColor()`，并遵循
`outlineEnabled()` / `outlineMainHand()` / `outlineOffHand()`，
per-item 规则经 `DisplayRuleManager.resolve`。

### 26.2 方法改名（重要）

`ItemInHandRenderer` 的方法**改了名**，照抄 1.21.11 的名字会在运行时注入失败：

| 1.21.11 | 26.2 |
|---|---|
| `renderHandsWithItems` | `submitHandsWithItems` |
| `renderArmWithItem` | `submitArmWithItem` |
| `renderPlayerArm` / `renderMapHand` / `renderItem` | 未变 |

`renderArmWithItem` -> `submitArmWithItem` 的改名就是本轮踩到的坑：编译通过，
但运行时 `InvalidInjectionException: Critical injection failure` 并直接崩溃。

- **但描边的实际视觉效果未经验证**：第一人称描边需要「世界内手持物品」，

## 13. 第一人称描边修复完成：26.2 的 reverse-Z

**结果：用户实机确认「描边正常了」。** 症状原为「描边是空心的，柔和度越小描边越细并且越卡顿」。

### 13.1 根因：深度约定从 normal-Z 翻转成 reverse-Z

26.2 把深度约定整体翻转了，三条独立证据：

1. `glClipControl`：`GlDevice` 初始化时调用 `ARBClipControl.glClipControl(36001, 37727)`
   = `(GL_LOWER_LEFT, GL_ZERO_TO_ONE)`。
2. `RenderPipelines` 里 `CompareOp.GREATER_THAN_OR_EQUAL` 出现 **14** 次，
   `LESS_THAN_OR_EQUAL` **0** 次。
3. vanilla 清深度一律用 `dconst_0` = **0.0**（`LevelRenderer` 的
   `clearDepthTexture(tex, 0.0)` / `clearColorAndDepthTextures(..., depthTex, 0.0)`）。

即：**近平面 = 1.0，远平面 = 0.0**（1.21.11 是近 0.0 / 远 1.0）。

实测验证：在渲染器里临时回读 mod 捕获的投影矩阵，得到
`m22 = 5.0025014E-4, m32 = 0.050025012, m23 = -1.0`。
按 26.2 约定解出 **near = 0.05、far = 100**（按 normal-Z 解会得到 near=100 > far=0.05，荒谬）。
→ reverse-Z 成立。

### 13.2 为什么表现为「空心 / 变细 / 卡顿」

共享着色器（`common/src/main/resources/.../shaders/core/`）里的深度比较全是 normal-Z 写法：

    visible = smoothstep(nearestDepth - 0.0004, nearestDepth + 0.0003, sceneDepth);
    if (sceneDepth + 0.00015 < nearestDepth) discard;

在 reverse-Z 数据下这套判断被整体取反，于是：

- 描边像素的可见性不再由「物品是否被遮挡」决定，而是由**背景深度与物品深度的巧合接近程度**决定
  → 只在背景恰好贴近物品的轮廓段上留下像素 → **断续、像空心的轮廓**；
- `sceneDepth` 稍微变化就从 1 掉到 0 → 取样方向稍有不同结果就跳变 → 看起来**细且抖**。

### 13.3 修法：在采样边界把深度镜像回来（单个开关，不动 1.21.11）

反向投影存储的深度**恰好**是 `1 - z`，所以在着色器里读到深度后立刻镜像回来，
下游所有 1.21.11 的数学就原样成立，不需要改任何比较式：

    float normalDepth(float depth) {
        return bloomParameters.z > 0.5 ? 1.0 - depth : depth;
    }

- 开关放在已有 uniform `OutlineInfo.bloomParameters.z`（原本恒为 0）。
- **26.2 的 Java 侧写 1.0**（`REVERSE_Z_FLAG`），**1.21.11 的 Java 侧不写**（仍是 0.0）
  → 同一份共享着色器，两边各按自己的约定工作，1.21.11 行为零变化。
- 涉及文件：`held_item_outline.fsh`、`held_item_bloom_composite.fsh`、
  `held_item_gui_composite.fsh`、`third_person_bloom_composite.fsh`（各 1～6 处采样点）。

**Java 侧同步修正**（原来全是 1.21.11 的 far=1.0）：
所有深度清除 `1.0D` -> `0.0D`，共 5 处：
`clearDepthTexture(mainTarget...)`、`clearDepthTexture(thirdPersonSceneDepth...)`、
`clear(TextureTarget)`、`clearMask(...)` 两处（含带 region 的重载）。
这一并修正了 1x1 arm-occluder 占位目标：它清成 0.0 后经 `normalDepth` 映射回 1.0，
`armDepthPresence(1.0) == 0`，即「没有手臂」——语义与 1.21.11 一致。

### 13.4 顺带修好：投影矩阵从未被捕获

排查中发现 `levelProjectionMatrix` / `handProjectionMatrix` **恒为 null**，

## 14. bloom「只有卡顿、没有效果」的结论：它就是 §13 那一处 reverse-Z

**用户实机确认：bloom 效果完全正常。bloom 代码本身不需要改。**

### 14.1 为什么之前看不到

`held_item_bloom_composite.fsh` 的主流程：

    float blurredCoverage = max(texture(BloomSampler, texCoord).a - texture(MaskSampler, texCoord).a, 0.0);
    ...
    bool hasVisibleItem = false;
    for (3x3) {
        float sampleItemDepth = texture(ItemDepthSampler, sampleUv).r;
        if (thirdPerson || texture(SceneDepthSampler, sampleUv).r + 0.00015 >= sampleItemDepth) {
            itemDepth = min(itemDepth, sampleItemDepth); hasVisibleItem = true;
        }
    }
    if (!hasVisibleItem) discard;

在 reverse-Z 数据下这个比较被取反：背景深度**永远小于**物品深度，9 个采样点全部不满足，
`hasVisibleItem` 恒为 false -> **整趟 pass 每个像素都 discard**。
而 2 次清屏 + 4 趟模糊 + 1 趟合成（每只手一套，共 7 趟 x2）照样发出 -> **只有卡顿、没有效果**，
和用户描述完全一致。§13 的 `normalDepth()` 让这个比较重新成立，bloom 随即正常。

### 14.3 顺带得到的两个实测结论（供后续参考）

1. **合成 scissor 仍为 null**。即使补上了 §13.4 的投影捕获，运行时 `resolveCompositeScissor` 依然返回 null。
   `isPerspectiveProjection`（`|m33| < 0.5`）对该投影成立，所以更可能是
   `state.itemBounds == null` 且 `itemPoseMatrix/modelViewMatrix` 缺失，或 `handPassMatrix` 在
   `snapshotRenderContext` 时尚未置位。纯性能项，不影响画面。
2. **两条回读路子在 26.2 都不可用**，后续做 GPU 侧诊断不要再走这两条：
   - `GlTextureView/`FBO 路子：`RenderSystem.getDevice()` 返回的是
     `com.mojang.blaze3d.systems.GpuDevice`（不是 `opengl.GlDevice`），`framebufferId()` 恒为 0；
   - `CommandEncoder#copyTextureToBuffer`：回调是**异步**的（实测 `callbackDone` 恒 false），
     同一帧内 `map` 读到的是空 buffer；
   - `glBindTexture` + `glGetTexImage`：在 26.2 的 DSA 上下文里对 color 纹理读回全 0。
   结论：GPU 侧诊断要么走 `PictureInPictureRenderer` 之类的正规通道，要么靠肉眼/日志推断。

### 15.1 之前为什么没有

### 15.2 移植内容

`ItemPreviewRenderer.renderToTexture` 现在按 1.21.11 的两遍结构重写：

1. 用 mod 自己的 `SubmitNodeStorage` + `FeatureRenderDispatcher` + `RenderBuffers(1)` 把物品
   **画进 PIP 颜色目标**，然后 `buffers.endFrame()` 刷出；
2. 建/复用私有 `outlineMask`（`TextureTarget(..., true, RGBA8_UNORM)`），清成
   `HeldItemOutlineRenderer.clearColor()` + `farDepth()`，把
   `RenderSystem.outputColorTextureOverride/outputDepthTextureOverride` 指向它，再提交一次物品并渲染，
   finally 里还原两个 override；
3. `HeldItemOutlineRenderer.compositePreviewToTexture(minecraft, config, outlineMask, colorTarget,
   depthTarget, resolvePreviewMaterialPalette(itemState, config), state.outlineScale())`。

**26.2 的关键差异（必须注意）：**

| 点 | 1.21.11 | 26.2 |
|---|---|---|
| `renderToTexture` 签名 | `(state, PoseStack)`，物品提交进 mod 自己的 storage | `(state, PoseStack, SubmitNodeCollector)` |
| 谁画物品 | mod 自己（super 不碰 storage） | **collector 是 PIP 自带的 storage，但 `prepare` 是在 `renderToTexture` 返回之后才 `renderAllFeatures` 回放它** —— 若把物品丢给 collector，物品会画在描边**之上** |
| 结论 | — | **必须自己提交+渲染物品，让 collector 保持为空**（`renderAllFeatures(空 storage)` 是 no-op） |
| `FeatureRenderDispatcher` | `(storage, BlockRenderer, BufferSource, AtlasManager, OutlineBufferSource, CrumblingBufferSource, Font)` + 无参 `renderAllFeatures()` | `(RenderBuffers, ModelManager, AtlasManager, Font, GameRenderState)` + `renderAllFeatures(SubmitNodeStorage)` |
| 刷帧 | `bufferSource/outlineBufferSource/crumblingBufferSource` 三个 endBatch | `RenderBuffers#endFrame()` |
| 清 mask 的深度 | `1.0D` | `HeldItemOutlineRenderer.farDepth()`（reverse-Z 远平面 = **0.0**） |

PIP 的 `prepare` 会先把 `outputColorTextureOverride/outputDepthTextureOverride` 指向 PIP 的纹理**再**调
`renderToTexture`（已用 `javap` 确认字节码顺序），所以 `renderToTexture` 里读到的两个 override 就是
PIP 的颜色/深度目标，与 1.21.11 一致。

顺带在 `HeldItemOutlineRenderer` 暴露了两个把 reverse-Z 知识集中的公共方法：
`clearColor()` 与 `farDepth()`，避免预览侧再硬编码 `0.0`。

### 16.7 光影下描边消失的真正原因：合成位置错了，不是深度比较

**症状**：带光影时描边完全不可见；日志显示拷贝与合成都正常：

    [IrisHandRoute] frame=7791 route=depthtex2 sceneOcclusionSetting=true depthtex2=copied texture=760 fbo=223 framebuffer=none
    [HeldOutline] frame=7802 composite main submitted target=854x480 radius=5.3333335 ...

**根因**：`renderItemInHand` 是在 `renderLevel` **内部**被调用的，而 Iris 把世界渲染进自己的 `colortex*`，
只在 `renderLevel` 末尾才用 final pass 覆写整个 `minecraft:main`。所以第一人称描边画进 main 之后，
**必然被 Iris 的 final pass 冲掉**——与深度比较正确与否无关。

**证据**：第三人称描边在光影下一直是正常的，而它早就被搬到了 `renderLevel` 之后
（`compositeThirdPersonAfterLevel` + 标记串 `"iris_render_tail"`）。第一人称没有做同样的搬迁，
这就是唯一的差别。

**修法**（与第三人称完全同构）：

- `composite(Minecraft)` 在 `isIrisShaderPackRendering()` 为真时不再当场合成，只置
  `handCompositePending = true` 并返回；
- 新增 `compositeHandAfterLevel(Minecraft)` 消费该标记，由已有的
  `compositeThirdPersonAfterLevel`（注入在 `renderLevel` 之后）调用——注意调用放在
  `THIRD_PERSON_CAPTURES.isEmpty()` 等提前返回**之前**，否则只有第三人称捕获时才会跑；
- 原合成主体改名为 `compositeHandNow(Minecraft)`；
- `beginFrame()` 复位 `handCompositePending`，避免某帧尾部没跑到时把旧捕获留到下一帧。

**关键点**：mask 重放（`renderCapture`）与 arm occluder 都只写 mod 自有目标，搬到尾部同样成立；
它们用的投影/模型视图是捕获时快照下来的（`state.projectionMatrix`/`modelViewMatrix`），
`renderCapture` 会自己恢复。**非 Iris 路径完全不变**（不置标记，行为与之前逐语句一致）。

新增 `[IrisHandTail] frame=... first-person composite reached the render tail` 限频日志，
用来确认"合成确实被搬到了尾部"。


### 16.8 仍然不可见的原因：Iris 下物品深度不可用，深度测试必须失效

搬迁到 render tail 后 `[IrisHandTail]` 正常出现、`depthtex2` 拷贝成功、合成已提交，
但描边仍不可见。结合代码自身证据可闭环解释：

- `held_item_bloom_composite.fsh` 里已有注释：**"Iris third-person replay uses a blank depth attachment"**
  ——Iris 下重放写入的深度是空的，所以 `ItemDepthSampler` 读到的是最远平面；
- 于是 `nearestDepth` ≈ 最远，而 `SceneDepthSampler`（`depthtex2`）读到的是真实场景深度（更近）；
- 裁剪着色器的 `sceneDepth + 0.00015 < nearestDepth` 因此**恒成立** → 每个描边像素都被 `discard`；
- 这与症状完全吻合：合成提交了、mask 有内容，但一个像素都没留下。

**结论：给这个测试一个"更准"的深度没有用，必须让它在 Iris 下失效。** 作者对第三人称也是这个思路
（`compositeThirdPerson` 里 `IRIS_SCENE_OCCLUSION_ENABLED=false` 分支的注释：
"an all-far scene depth makes the shader's occlusion test a no-op, so the outline survives everywhere
it can rasterise"）。

**改动**：`IRIS_HAND_SCENE_OCCLUSION_ENABLED` 默认由 true 翻为 **false**，即第一人称在光影下默认
**不做场景深度测试**（`occlusionMode = OCCLUSION_OFF`）。语义上等于把场景项整段跳过，比喂一张
全远深度图更干净，也避免一次 GL blit。手臂遮挡不受影响——arm occluder 是 mod 自己重放的
coverage mask，与场景深度无关（这正是 §16.5 把它移出遮挡块的原因）。

`-Ditemglintrelight.irisHandSceneOcclusion=true` 可重新打开 `depthtex2` 测试，供继续实验。

**代价**：光影下描边不会被墙/方块遮挡（场景遮挡丢失）。这是拿不到可信物品深度时的必然取舍；
要恢复它必须先解决"Iris 下重放深度为空"这个更底层的问题。


### 16.9 真因确认：mask 是空的（Iris 接管了手部渲染）

**实测（带光影，`IRIS_HAND_SCENE_OCCLUSION_ENABLED=false`）**：

    [MaskProbe] callback=false/false maskMaxAlpha=0 frameMaxAlpha=255 armMaxAlpha=-2 \
                maskTarget=854x480 scissor=null armReady=false captured=true

- `frameMaxAlpha=255`：对照组（主画面）非零 -> **回读机制有效**，所以
- `maskMaxAlpha=0`：**mask 完全是空的**；
- `armReady=false` -> 手臂遮挡是 1x1 占位，`armOcclusion` 返回 1.0，不是它；
- `scissor=null` -> 没有裁剪。

结论：描边没有源。与深度无关、与合成时机无关——**重放根本没写进 mod 的 mask 目标**。

**Iris-26.2 源码给出的原因**（逐条 file:line）：

| 位置 | 行为 |
|---|---|
| `mixin/MixinGameRenderer.java:77` | `@Redirect` 掉原版 `renderItemInHand` 里的 `submitHandsWithItems` 调用，**光影开启时直接 `return`（整个不调）**，手部交给 Iris 自己画 |
| `mixin/MixinItemInHandRenderer.java:29` | 对 `submitArmWithItem` HEAD `@Inject(cancellable=true)`，Iris 接管每只手臂的物品提交 |
| `mixin/MixinPreparedRenderType.java:18` + `layer/EntityRenderStateShard.java:10` | 每个 entity/item 渲染类型的 draw 都被 `@WrapMethod` 包住，`setup()` 调 `GbufferPrograms.beginEntities()` —— **换掉 Iris 的实体 program** |

即：mod 抓到的提交节点，经游戏 `FeatureRenderDispatcher` 重放时，实际执行的是 **Iris 的实体 program**，
配合 Iris 的 gbuffer 绑定；我们的 mask 目标因此收不到任何像素。

**另外查实一个 26.2 的新机制**（对任何离屏重放都有用）：
`PreparedRenderType.drawFromBuffer` 的字节码显示——颜色附件**优先**用
`RenderSystem.outputColorTextureOverride`（非空时生效），但**深度附件只来自
`outputTarget.getRenderTarget()`，且当该 target 的 `useDepth == false` 时直接传 `null`**，
完全忽略 `outputDepthTextureOverride`。所以"重放进自定义目标"在 26.2 只对颜色成立，深度不可靠
——这与 bloom 着色器里那句 "Iris third-person replay uses a blank depth attachment" 是同一件事的根。

### 16.10 可选方案（需要决策，不是小修）

| 方案 | 内容 | 代价 |
|---|---|---|
| A. 光影下关闭第一人称描边 | `isIrisShaderPackRendering()` 为真时直接跳过 capture+composite | 光影下没有第一人称描边，但**不做无用功、不卡**；实现 5 行 |

**建议**：要光影下也有描边就做 B（并接受特殊模型无描边）；否则做 A。第三人称的 Iris 路线走的是同一套重放，

## 18. P2 续：GUI 描边真正跑通（三个决定性缺陷）

§17 只做到"编译通过 + mixin 应用成功"。本轮把链路真正跑起来，发现并修掉三个缺陷——**其中两个是能让整类问题静默通过的元级缺陷**。

### 18.1 缺陷一（元级）：mixin 配置键名拼错，全 mod 的注入都容忍找不到目标

配置里写的是 `"injectors": {"require": 1}`，而 Mixin 的正确键名是 **`defaultRequire`**
（Iris 自己的配置就是 `"defaultRequire": 1`）。写错等于该项被忽略 -> 默认 require 为 0 ->
**任何 `@Inject` 找不到目标方法都不会报错**。

后果：`GuiGraphicsItemOutlineMixin` 的两个注入点指向 **26.2 里根本不存在的方法**，
客户端启动、运行、退出全程**一个警告都没有**。这正是"编译通过 != 运行时可应用"的最阴的一层。

**已修**：改为 `"defaultRequire": 1`。改完后测试运行仍然 **零 mixin 失败** ->
说明 mod 里没有其它失效注入（这本身是有价值的确认）。

### 18.2 缺陷二：两个注入点的目标在 26.2 已改名/改签名

| 旧目标 | 26.2 现状 | 修正 |
|---|---|---|
| `GuiGraphicsExtractor#renderItem(LivingEntity,Level,ItemStack,III)` | **改名为 `item`**，且这个 6 参重载是 **private**；所有公开 `item(...)` 重载都汇聚到它 | 目标改 `item(...)`；private 方法 Mixin 可注入。其局部变量 `itemStackRenderState` 正是 `TrackingItemStackRenderState`（`javap -l` 确认），`LocalCapture.CAPTURE_FAILSOFT` 可用 |
| `GuiRenderer#submitBlitFromItemAtlas(GuiItemRenderState,float,float,int,int)` | 改为 `(GuiItemRenderState, GuiItemAtlas$SlotView)`（槽位视图取代了散开的 u/v/尺寸） | 目标改新签名；manager 只读 render state，其余不用改 |
| `GuiGraphicsExtractor#renderTooltip(...)` | **不存在**：26.2 改成 `setTooltipForNextFrame` 家族 + 一个 deferred runnable | 去掉 `beginTooltipRender`/`endTooltipRender` 两个注入。tooltip 里的物品走的是同一个私有 `item(...)`，因此**照样被捕获**——差别只是 tooltip 物品预览也会带描边（副作用是正面的） |

### 18.3 缺陷三（本轮真正的根因）：`beginFrame` 挂在了错误的帧阶段

26.2 把一帧拆成 **`GameRenderer.extract`（构建渲染状态）-> `GameRenderer.render`（消费）**：

- GUI 物品的**捕获**发生在 `extract` 期间（`GuiGraphicsExtractor.item` -> `capture()`）；
- GUI 物品的**提交**发生在 `render` 期间（`GuiRenderer.submitBlitFromItemAtlas` -> `submit()`）；
- 而 `GuiItemOutlineManager.beginFrame()`（清理 `CAPTURES`）被接在了 `GameRenderer.render` HEAD
  —— **正好夹在两者中间**，于是每帧都把刚捕获的东西全清掉，`submit` 永远 `CAPTURES.remove() == null`。

实测证据（临时探针，已移除）：

**已修**：把 `GuiItemOutlineManager.beginFrame()` 移到 `GameRenderer.extract` HEAD
（`HeldItemOutlineRenderer.beginFrame()` 保持在 `render` HEAD 不动：它的手部捕获发生在 render 期间）。

### 18.6 给第三人称移植的教训清单（从第一人称与 GUI 两轮中提炼）

1. **`injectors.defaultRequire` 拼错会让全 mod 的 `@Inject` 静默容忍找不到目标**（§18.1）。已修，
   且修后仍零失败。移植新 mixin 前**必须用 `javap` 逐个核对目标方法名与描述符**，不能只信编译。
2. **26.2 的一帧是 `extract`(建状态) -> `render`(消费)**。任何"捕获/提交"配对的东西必须确认两者
   落在同一帧的同一侧；帧边界钩子挂错阶段会静默清掉当帧数据（§18.3）。
3. **Iris 会替换每条原版管线的已编译 program，并对 IrisProgram 跳过 `glDrawBuffers`**
   -> 经游戏渲染类型重放进自定义目标会写不进去。`HeldItemOutlineRenderer.renderCapture` 现在统一在
   重放期间置 `ImmediateState.bypass`（§16.9 / 2fe5ced），第三人称复用同一函数故同样受保护。
4. **不要用 `copyTextureToBuffer`/`glGetTexImage` 做回读判断**：源纹理需 `USAGE_COPY_SRC`，
   mod 自建 `TextureTarget` 未必带；用户实机截图才是可靠证据（§16.9）。
5. **`wrapStorage` 每帧可能被调用多次**（Iris 手部 solid/translucent 两遍），storage 只能每帧分配一次（§16.9 / 2025a99）。
6. **静默 catch 是定位杀手**：本次 GUI 的 `catch (RuntimeException)` 吞掉了合成失败。新增渲染路径不要静默吞。

### 19.2 恢复 phase one：26.2 没有 `MultiBufferSource`，主批次 = `PreparedFrame#executeSolid`

`compositeThirdPersonAfterMainBatch(...)` 此前是死代码：1.21.11 由 `BufferSourceMixin` 挂在
`MultiBufferSource.BufferSource#endBatch` TAIL，并用 `bufferSource == renderBuffers.bufferSource()` 过滤；
26.2 删掉了这个类（`BufferSourceMixin` 也随之作废），于是没有任何调用点，
`capture.sceneDepthReady` 永远是 false。

`javap -c LevelRenderer` 实测 `lambda$addMainPass$0` 的执行顺序：

    renderGroup(OPAQUE) -> executeSolid() -> [Iris: pipeline.beginHand + HandRenderer.renderSolid]
      -> executeTranslucent() -> executeOutline() -> renderGroup(TRANSLUCENT) -> executeTranslucentAfterTerrain()

`executeSolid()` 就是"实体/物品主批次"，且它落在不透明地形之后、半透明地形/云/天气之前——与旧钩子
同一位置。因此：

- 新增 `mixin/client/FeatureRenderDispatcherFrameMixin.java`：
  `@Mixin(FeatureRenderDispatcher.PreparedFrame.class)` +
  `@Inject(method = "executeSolid", at = @At("RETURN"))` -> `compositeThirdPersonAfterMainBatch(Minecraft)`；
- 该方法去掉 `Object bufferSource` 形参与那段恒等判断：26.2 里"是哪一次 endBatch"这个过滤条件不存在了，
  调用点本身就是过滤器。

**为什么值得恢复**：没有快照时第三人称只能退化到 `renderLevel` 之后的"当前帧深度"，那时半透明地形/云
已经写进去了，描边会被水面/云裁掉；Iris 分支也拿不到"不含物品的不透明场景深度"，只能退回 `depthtex2`
（那份深度里带着物品自己，正是 §16 里"合成正常却看不见"的同类问题）。

**Iris 下这一步为什么仍成立**：Iris 替换的是**已编译 program**；`MixinGlCommandEncoder` 只对
`IrisProgram` 跳过原版的 `glDrawBuffers`（即颜色附件交给 Iris 的 DRAWBUFFERS），它的两个
framebuffer 相关重定向最终都落回原版 pass 自己的 FBO，深度附件没有被替换（Iris 自建的
`GlFramebuffer`/`GL_DEPTH_ATTACHMENT` 只用于它自己的 custom pass）。所以那一刻 `main` 的深度就是
不透明地形深度。诊断开关 `-Ditemglintrelight.irisOpaqueSnapshot=false` 可退回旧的 `depthtex2` 路线。

**重复调用**：`executeSolid` 每帧会被调用不止一次——Iris 的 `HandRenderer.renderSolid` 里还有一次
`featureRenderDispatcher.renderAllFeatures` -> 它自己的 `executeSolid()`。`snapshotThirdPersonSceneDepth`
的 `thirdPersonSceneDepthFrame == frameNumber` 早退保证每帧只快照一次，而那一次必然来自主 pass（主 pass 的
`executeSolid()` 早于 Iris 的注入点）。Iris 阴影 pass 也会走关卡渲染，但 `thirdPersonPipelineActive` 里的
`isIrisShadowPass()` 与"无待合成捕获"两道闸门会挡住它。

### 19.3 修掉第三人称 bloom seed 的 reverse-Z（§13 遗留 TODO）

## 21. 第三人称遮挡修复：快照挂错了帧阶段（根因已由字节码证实）

**症状（用户实机）**：不管有没有光影，第三人称描边都穿过玩家自己的身体、也穿过本该盖住它的东西。

### 21.1 根因：26.2 的主批次不是 `executeSolid`

上一轮我把「不透明场景深度快照」挂在了 `PreparedFrame#executeSolid` 的 RETURN，理由是
"executeSolid 就是旧 `endBatch` 的位置"。**这个判断是错的**，而且错得很隐蔽：它编译、能跑、
快照也确实被写入，只是**里面没有玩家**。

`javap -p -c LevelRenderer` 实测主 pass 的执行顺序：

    renderGroup(OPAQUE) -> executeSolid() -> executeTranslucent() -> executeOutline()
        -> renderGroup(TRANSLUCENT) -> executeTranslucentAfterTerrain()

`javap -p -c PreparedFrame` 实测两件事：

1. `executeSolid()` 只执行每个 `SubmitNodeCollection` 的 **`solid`** 阶段
   （`getfield SubmitNodeCollection.solid` -> `executePhase`）；
2. `executeTranslucent()` 执行的是 `shadows`、**`translucentModels`**、`seeThroughNameTags`、`nameTags` …

再看 `SubmitNodeCollection.submitModel` 怎么分流（字节码）：

    RenderType.isOutline()  -> outline 阶段
    否则若命中 solid      -> SimpleFeatureRenderPhase.submit
    否则 RenderType.hasBlending() -> TranslucentFeatureRenderPhase.submit   // translucentModels

而**玩家的身体就是带混合的类型**：`LivingEntityRenderer.getRenderType` 返回
`RenderTypes.entityTranslucentCullItemTarget(texture)` 或 `model.renderType(texture)`（人类模型即
`entityTranslucent`）——两者都 `hasBlending() == true`。

**结论**：玩家（以及同样带混合的其它实体）的模型在 `executeTranslucent()` 才被画出来，比我的快照点晚一步。
所以快照里只有地形，没有身体 -> 着色器的 `sceneDepth + eps < itemDepth` 在身体所在像素上恒为假 ->
描边直接盖在身体上。用户报的两件事（穿过身体、穿过多 mob/实体）是同一个原因。

**为什么第一人称一直正常**：第一人称合成分两步用的都是**主目标当时的实时深度**
（`mainTarget.getDepthTextureView()`），不存在"取早了一帧阶段"的问题；第三人称才是那个用了中间目标
`thirdPersonSceneDepth` 的路径。1.21.11 之所以没这个问题：它挂的 `BufferSource.endBatch` 冲刷的是
**所有**已缓冲的实体几何（solid 与 translucent 一起），本来就晚于身体。

### 21.2 修法

1. **钩子换到 `executeOutline()` HEAD**（`FeatureRenderDispatcherFrameMixin`）：它在
   `executeSolid` 与 `executeTranslucent` **之后**、`renderGroup(TRANSLUCENT)` **之前**，
   且是无条件调用（`ifnull`/`ifeq` 都不经过它；`executeAlwaysOnTop` 才是条件调用）。
   即 1.21.11 `endBatch` 的等价位置：所有要素阶段之后、半透明地形/云/天气之前。
2. **快照改成整幅拷贝**：`copyDepthRegion(thirdPersonSceneDepth, mainTarget, null)`。
   1.21.11 的 `framebufferId` 从来没解析成功（§12.2 是 26.2 才修的），所以它那条路**从来只走**
   引擎的 `RenderTarget#copyDepthFrom`（整幅）；26.2 修好 FBO 查找后，这一步悄悄换成了自写的区域 blit。
   区域本身只省下一次 depth 拷贝，不值得再留着"快照可能只覆盖一块"的风险。
   掩码的 seed 同理改成整幅拷贝（`copyDepthRegion(sceneDepth, thirdPersonSceneDepth, null)`）。
3. **留一个逃生开关** `-Ditemglintrelight.thirdPersonLiveDepth=true`：直接用实时帧深度做遮挡测试与
   seed（等价第一人称的做法）。快照是"在固定时点取的一份拷贝"，实时深度则是"绑在哪就读哪"，
   不会再有时点问题；代价是半透明地形也会挡住描边（水下的描边会随水面消失）。
   诊断输出里 `irisNoHandDepthStatus` 会显示 `live_depth`。

### 21.3 本轮核对（全部来自 jar 的 javap，没有跑 runClient）

| 结论 | 证据 |
|---|---|
| 主 pass 阶段顺序 | `lambda$addMainPass$0` 的调用序列 |
| `executeSolid` 只跑 solid 阶段 | `getfield SubmitNodeCollection.solid; executePhase` |
| `executeTranslucent` 跑 translucentModels 等 | 同一方法的多个 `executePhase` |
| 带混合的模型进 translucentModels | `SubmitNodeCollection.submitModel` 里的 `RenderType.hasBlending()` 分支 |
| 玩家身体是带混合类型 | `LivingEntityRenderer.getRenderType` -> `entityTranslucentCullItemTarget` / `model.renderType` |
| `executeOutline` 无条件调用 | `aload 6; invokevirtual executeOutline` 前后无分支，紧跟 `renderGroup(TRANSLUCENT)` 之前 |

`classes` 编译 0 错误。**视觉效果需要用户实机确认**：身体/其它实体是否已正确遮挡描边；
若仍有异常，先用 `-Ditemglintrelight.thirdPersonLiveDepth=true` 判断是"快照内容"问题还是"合成/裁剪"问题。

## 22. 收尾：`beginMainWorldPass` 接回 + 显示规则 / 盔甲 / 盔甲架 现状审计

### 22.1 补上 26.2 的 START_MAIN 等价钩子（这是移植清单里最后一个真实缺口）

`ItemGlintRelightClient` 里那条 TODO（"WorldRenderEvents was removed"）对应 1.21.11 的：

    WorldRenderEvents.START_MAIN.register(context -> HeldItemOutlineRenderer.beginMainWorldPass());

`beginMainWorldPass()` 本体在 26.2 里**一直在，只是没人调用**（全树扫描确认：0 个调用点）。它的作用是
丢弃 shader 预 pass（含阴影 pass）留下的手部捕获状态（`recordingHand/submittingHand/*Depth/storageWrapped`
与 MAIN_HAND/OFF_HAND）。

新增 `mixin/client/LevelRendererMainPassMixin`：

- `@Inject(method = "addMainPass(...)", at = @At("HEAD"))` -> `beginMainWorldPass()`；
- **为什么是 `addMainPass`**：Iris 的阴影 pass 是从 `LevelRenderer#render` 里 **`addMainPass` 调用点**上注入的
  （`MixinLevelRenderer.iris$renderTerrainShadows`），所以在方法本体的 HEAD 上，预 pass 已经全部跑完、
  主世界 pass 正要开始——这正是 `START_MAIN` 的语义。`LevelRenderer#render` 的 HEAD 太早（预 pass 还没跑），
  而 `executeSolid` 等要素阶段在 pass 内部，更晚。
- **对手部捕获安全**：`javap` 实测 `GameRenderer#renderLevel` 先调用 `LevelRenderer#render`（offset 405），
  之后才调用 `renderItemInHand`（offset 508），所以钩子触发时手部窗口还没打开；Iris 下额外的手部渲染也在
  主 pass 内部（更晚）。
- 目标描述符机械比对通过：`addMainPass` 的描述符与"编译产物里 handler 去掉 `CallbackInfo`"逐字符相同。
